# 变更影响分析 Playbook

## 影响面模型

工程变更不能只看被修改的函数。分析至少覆盖五层：入口 API 或配置、组件调用关系、持久化状态与索引、外部依赖与运行资源、监控和回退路径。每一层都要回答谁消费它、失败如何传播、旧版本能否继续工作、怎样证明变更安全。

## Reranker 替换案例

把启发式 Reranker 切换成 Cross-Encoder 会影响检索延迟、模型依赖、启动与首次请求行为、CPU/内存预算、离线部署和排序分数分布。配置必须保持默认策略可用；Cross-Encoder 应延迟加载，加载失败后回退到启发式，并在指标中记录实际策略和原始错误。

调用方不应依赖某个模型的原始分数绝对值。排序质量需要用固定 JSONL 评测集比较 Source Hit、MRR 和 p95 延迟，不能只凭单个示例。上线应先小流量观察延迟、错误率与资源，再决定扩量；回退只需恢复 Reranker 配置，不应要求重建文档数据。

## Embedding 变更案例

更换 Embedding 模型会改变向量维度和空间分布，既有索引不可直接复用。变更前必须记录模型名、revision、维度和归一化方式；变更时构建独立新索引并做双读评测；切流后保留旧索引直到观察窗口结束。维度不匹配应在加载阶段失败，不能等到查询时才返回模糊错误。

## 状态图变更案例

为 Verification Loop 增加重试或回退时，要同时检查最大尝试次数、最大图转换次数、Checkpoint 序列化、重复工具调用和终止后的状态清理。重试输入必须发生有效变化，且每轮保留失败原因；无界循环或静默吞错都属于阻断合并的风险。

## 输出要求

影响分析输出应包含变更边界、受影响组件、兼容性风险、数据或状态迁移、失败与回退路径、验证计划和仍缺少的证据。无法从材料确认的内容标记为待验证，不推测成事实。
